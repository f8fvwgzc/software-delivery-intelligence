# Privacy notice

This notice describes what personal data Software Delivery Intelligence
("SDI") processes, why, for how long, and what rights you have. It is
written to be used as-is by whoever operates an SDI instance; an operator
fills in the **Contact** section at the end and is the controller for the
instance they run. The engineering detail behind every statement is in
[`TRUST.md`](TRUST.md) and [`CONTRACT.md` §18–§19](CONTRACT.md#18-identity-workspaces-and-tenancy).

## 1. Roles

- **Individual user**: you sign in with your GitHub account and connect
  repositories you own. The operator of the instance is the controller of
  the data SDI stores about you; if you self-host, that is you.
- **Organisation**: an organisation owner installs the SDI GitHub App. The
  organisation (through the operator running the instance) is the
  controller for the data of its members; SDI processes that data on the
  organisation's instructions, expressed as the App's repository selection
  and the workspace's data controls.
- **The SDI project** (the authors of this software) is not a party to any
  of this. The software contains no channel back to its authors: no
  telemetry, no licence check, no update ping.

## 2. Data categories

| Category | Examples | Source | Why |
|---|---|---|---|
| **Account identity** | GitHub user id, login, display name, avatar URL, primary email | GitHub OAuth (`read:user`, `user:email`) | To know who is signed in, show it in the UI, attribute decisions and audit entries |
| **Session** | opaque session token (in the `sdi_session` cookie), creation and expiry time | generated by SDI | To keep you signed in for up to 30 days without re-authorising |
| **Workspace membership** | organisation role, team names that map to SDI roles, optional admin-set lower role | GitHub organisation API, `member` and `team` webhooks | To decide what you may do in a workspace (`VIEWER` … `OWNER`) |
| **GitHub credentials** | OAuth access token (encrypted at rest), short-lived installation tokens (memory only) | GitHub | To read repositories, workflow runs and deployments on your or the organisation's behalf |
| **Repository knowledge** | facts, dependency graph, maturity scores, pipeline and deployment metadata, short text chunks and embeddings, the file tree, cached file contents (per the `code_cache` setting) | your repositories | The product: understanding how the repository is delivered |
| **Work product** | proposals, negotiation messages, decisions, generated documents and diagrams, execution logs | created by you and by SDI in your workspace | The product |
| **Audit trail** | actor, action, target, timestamp | generated by SDI | Accountability: who connected, approved, executed, exported or deleted what |
| **Workspace-owned LLM key** | an API key for the model provider you chose (encrypted; last four characters shown) | entered by an admin | Only if you turn the reasoner on; SDI never uses a key you did not provide |
| **Operational logs** | request id, route, status, timing, the client address at the edge | nginx and the services | Debugging and abuse prevention; no request bodies, no tokens |

Repository contents can incidentally contain personal data (author names
in commit history are *not* read; names and emails in source files or
documentation may be). SDI treats file contents as data about the
repository, caches them only as the `code_cache` setting allows, and never
displays files that look like secrets.

## 3. Retention

| Category | Retained |
|---|---|
| Account identity, membership | While you are a member of at least one workspace on the instance; removed with the last workspace or on request |
| Session | 30 days from sign-in, or until you sign out, revoke the GitHub grant, or the operator rotates `SDI_SESSION_SECRET` |
| OAuth token | Session lifetime, encrypted |
| Installation tokens | At most 55 minutes, in memory only |
| Repository knowledge | Until the project is disconnected (tree: latest commit only; file contents: per `code_cache`, default 24 hours) |
| Work product, execution logs | Until deleted by a member with the right role, or with the workspace |
| Audit trail | `audit_retention_days` per workspace, default 365; 0 keeps entries indefinitely |
| Operational logs | Rotated by the container runtime (three files of 10 MB per service in the shipped compose file); the operator may ship them elsewhere and is responsible for that copy |
| Backups | Operator-defined; see `docs/self-hosting.md`. A workspace deleted from the live database still exists in backups until those expire |

## 4. Lawful basis

Wording for operators in jurisdictions that require a stated basis (GDPR
and similar). Delete what does not apply.

**For individual users.** We process your account identity, session and
GitHub credentials because they are necessary to provide the service you
asked for when you signed in (performance of a contract, GDPR art. 6(1)(b)).
We process the knowledge SDI derives from repositories you connected on the
same basis. We keep an audit trail and operational logs because we have a
legitimate interest in the security and accountability of the instance
(art. 6(1)(f)); the audit trail contains only actions you took in the
product. Sending structured context to a model provider happens only after
a workspace admin turns the reasoner on and supplies a key, which we treat
as the controller's instruction; the provider's own terms govern what they
do with it.

**For organisations.** The organisation that installs the SDI GitHub App
decides which repositories SDI may read and which members may use it, and
is the controller of the resulting data; the operator processes it under
the organisation's instructions. Member identity and roles are derived from
GitHub organisation membership, which the organisation already maintains
for its own purposes. The basis for processing members' data is the
organisation's legitimate interest in understanding and improving how it
delivers software (art. 6(1)(f)), balanced by the facts that SDI reads only
what GitHub already lets those members read, shows nothing about a member
beyond their GitHub identity and their actions in the product, and derives
roles rather than inventing new ones. Organisations that need a data
processing agreement with their operator should attach this notice and
`TRUST.md` to it as the description of processing.

## 5. GitHub permissions and why each is requested

**OAuth sign-in (individuals).** Scopes: `read:user` and `user:email` (who
you are); `repo` is requested only for the personal workspace, because
GitHub has no read-only OAuth scope for private repositories. SDI uses it
to read; the `github` execution adapter writes a pull request only when you
accept a plan that opens one.

**The SDI GitHub App (organisations).** Permissions, from `CONTRACT.md` §18:

| Permission | Level | Used for |
|---|---|---|
| Contents | read | Repository tree and the files the analyzer wants; tarball download for Docker dry runs |
| Metadata | read | Repository list, default branch, visibility (mandatory for any App) |
| Actions | read | Workflow definitions and runs, to classify pipelines and detect CI maturity |
| Deployments | read | Deployment history, to detect environments and release cadence |
| Pull requests | write | Only the `github` execution adapter, to open the pull request a plan was approved to open. Nothing else writes. |
| Members | read | Organisation membership and teams, from which workspace roles are derived |

Events subscribed: `installation`, `installation_repositories` (create
and remove workspaces, track the repository selection), `push`,
`pull_request` (keep facts fresh), `member`, `team` (keep roles fresh).
Every delivery is verified against the webhook secret before it is read.

The App is installed per organisation and can be limited to selected
repositories; SDI never sees repositories outside that selection.
Uninstalling the App removes the workspace and everything in it.

## 6. Where data goes

- **GitHub**: every read described above; a pull request when you
  approved one.
- **A model provider** (Anthropic by default): only when the reasoner is
  on, with the workspace's own key, structured context only (facts,
  options, a spec). No file contents, no identities beyond what you put in
  a negotiation message.
- **Nowhere else.** There are no sub-processors built into the software.
  An operator who adds some (hosting, backups, log shipping) lists them in
  the Contact section below.

## 7. Your rights

Regardless of jurisdiction, the product gives you:

- **Access and portability**: `POST /api/v1/workspaces/{id}/data/export`
  returns everything stored for a workspace as JSON; the audit route lists
  every action taken in it.
- **Erasure**: `DELETE /api/v1/workspaces/{id}` (owner) removes the
  workspace from every schema; `purge-code-cache` removes cached file
  contents immediately; disconnecting a project removes its knowledge.
- **Restriction**: the data controls (`code_cache`, `minimal_chunks`,
  `reasoner`, `audit_retention_days`) narrow what is stored.
- **Withdrawal**: sign out, or revoke the OAuth grant or uninstall the App
  on GitHub; access ends at the next request.

For anything the product cannot do itself (correcting a derived fact,
erasing your identity from another workspace's audit trail, a copy of a
backup), contact the operator.

## 8. Changes

This notice changes with the software. The version that applies is the one
in the repository at the commit the instance runs; the operator should
expose the running version (`GET /api/v1/system/status`) next to it.
